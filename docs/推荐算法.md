# 推荐算法

## 一句话

每个游戏是 tag 空间里的一个向量，用户画像是几个游戏向量加减出来的另一个向量，推荐就是找夹角最小的、同时正在打折的。

## 1. tag 空间怎么建

**来源**：SteamSpy `appdetails.tags`，固定给你 top-20 tag + 票数（如 `Souls-like: 6994, Open World: 5078`）。
没有更长的列表了 —— 实测 Steam 商店页 HTML 里也只有 20 个 `app_tag`，这是上限。

**游戏向量**（`recommend.build_index`）：

```
tf(t, g)  = log1p(票数)                    # 票数是社区累计标记次数，天然反映强弱
idf(t)    = log((1+N) / (1+df(t))) + 1     # N = 库内游戏数，df = 带该 tag 的游戏数
v_g[t]    = tf(t,g) × idf(t)，然后 L2 归一化
```

用 log 压票数是为了不让「Open World 5000 票」把「Metroidvania 300 票」彻底吃掉；
idf 是为了压「Indie」「Action」这种人手一个的 tag —— 它们几乎无区分度。

## 2. 画像怎么来

数据来自 `profile_entries` 表，两种粒度都吃：

| 输入方式 | 例子 | 处理 |
|---|---|---|
| 只给名字 | `只狼` | `resolve_entry` 在本库名字/中文名里做完全匹配 → 包含匹配，命中就用该游戏的向量 |
| 名字 + 说喜欢哪儿 | `只狼 喜欢招架手感，不要迷路` | 先解析名字，剩下的描述走 `tags.extract()` 抽 tag，以 0.8 权重叠加 |
| 纯描述 | `想要有构筑深度的回合制，不要恐怖` | 全部走文本抽取 |
| 不喜欢 | `kind=disliked` | 权重取负，进画像时减掉 |

**聚合**：

```
p = Σ_e  sign(e) × w_e × vec(e)        # sign: liked=+1, disliked=−1
p = L2_normalize(p)
```

负权重保留（`_norm` 不过滤负数），效果是：主打被你否定 tag 的游戏余弦会掉下来，
而不是只靠「正向 tag 缺失」间接降权。

**自然语言怎么落到 tag 上**（`radar/tags.py`）：

1. 一张 ~180 条的口语 → Steam tag 别名表，覆盖中文口语（魂类 / 肉鸽 / 银河城 / 战棋 / 种田 / 手感 / 招架……）。
2. 长别名优先匹配，避免「肉鸽卡牌」被「肉鸽」抢走。
3. 否定判定：别名前 12 字内出现「不要 / 讨厌 / 受不了 / 避开……」，或后 6 字内出现「不要 / 算了 / 腻了」，
   该 tag 进 `negative` 而不是 `positive`。
4. 剩下没认出来的中文按 2~3 字窗口收集，英文剩下 4 字以上的词收集，一起塞进 `unmatched` 返回给界面 ——
   **听不懂的词要显示出来**，否则永远不知道词表该补什么。

## 3. 打分与排序

```
raw     = cos(p, v_candidate)                     # 已归一化，点积即余弦
adj     = raw × (1 + 0.30 × discount/100)         # 折扣加成：90% off 相当于 ×1.27
过滤     : 已拥有 / 已输入过 / 已 dislike 的排除；命中 tag < 2 个的丢弃（防偶然相似）
排序     : adj 降序
```

每条结果额外算三个价格标记：

- `at_low`：现价 ≤ 本库历史快照最低价 → 就是史低；
- `near_low`：现价 ≤ 史低 × 1.10；
- `price / list_price / discount / shop`：当前最便宜那家店。

**为什么推荐和史低是一张表**：用户要的不是「推荐列表」和「史低列表」两个功能，
而是「我可能喜欢、而且现在便宜」的东西。所以打分里带折扣项，列表里带价格和史低标记。

## 4. 可解释性

每条推荐都带 `matched_tags`（贡献最大的 tag 及贡献值），界面直接显示。
用户能立刻判断「它为什么给我推这个」—— 不对就回去改画像，这套闭环比任何调参都有效。

`python -m radar.cli profile` 会打印画像 top-15 tag，并标出每个 tag 是从哪句口语命中来的。

## 5. 已知局限（诚实版）

1. **候选池质量决定上限**。现在靠 Steam 特惠 + CheapShark + SteamSpy 榜单铺，
   覆盖不了长尾；要全量得跑 `request=all`（几百页，另说）。
2. **tag 只有 20 个**。Steam 侧没有更细的标签，所以「招架手感」这类要求只能落到
   `Character Action Game` / `Souls-like` 这种粗粒度上，做不到「只推有弹反的」。
3. **没有真实玩时长信号**。`appreviews` 匿名 302、SteamSpy 的 `average_forever` 全为 0，
   所以目前「玩得久 = 更喜欢的」这条只能靠用户手填 `weight`。
   接了 `steam_api_key` + 公开 profile 后可以用 `GetOwnedGames.playtime_forever` 补上。
4. **没做 MMR 去重**。同一套 tag 组合的游戏（比如一堆 `Roguelike Deckbuilder`）会挤在一起，
   需要的话在 `recommend()` 后面加一步 MMR（`λ·score − (1−λ)·max_sim(picked)`，λ≈0.7）。
5. **文本 ← tag 的映射靠人工词表**，没用模型。好处是可解释、可迭代、零依赖；坏处是没覆盖的说法一律进 `unmatched`。
